# Kenshi Shield: спецификация первого релиза

Дата: 2026-10-10.
Статус: проект спецификации для одобрения перед реализацией.
Репозиторий: https://github.com/kenshiro-pixel/kenshi-shield

## 1. Назначение и пределы защиты

Kenshi Shield управляет безопасной настройкой Linux VPS с существующими Remnawave Panel, Remnanode/Xray и Nginx/Caddy. Установка этих сервисов, изменение подписок, пользователей, тарифов и ключей VPN не входят в его обязанности.

Инструмент сокращает ненужную сетевую доступность, ограничивает исходящий SMTP abuse и позволяет контролируемо подключать поведенческую защиту. Он не гарантирует защиту от распределённой атаки и не устраняет переполнение канала VPS. Для объёмных атак требуется провайдерская фильтрация или подходящий внешний сервис.

Безопасность определяется проверенной топологией, минимальными правилами и восстановлением, а не количеством установленных защитных пакетов.

## 2. Доставка и расположение GUI

- GitHub содержит публичный исходный код, инструкции и версионированные Releases.
- Пользователь скачивает выпуск для своей ОС, проверяет его происхождение и запускает локальное приложение.
- Go-приложение обслуживает встроенный GUI только на loopback. Публичного сервера управления или GitHub-hosted SSH-посредника нет.
- GUI открывается в браузере на рабочем компьютере. GitHub Pages, если появится, используется только для документации.
- На VPS по SSH доставляется совместимый исполнитель. Он не открывает сетевой listener.
- После установки правила и автономное восстановление работают без включённого пользовательского компьютера.
- Публикация релиза, push и изменение настроек GitHub выполняются только по явному разрешению владельца.

## 3. Выбор стека

Основной стек: Go для CLI, локального API, SSH-оркестрации и Linux-исполнителя; React/TypeScript для GUI; SQLite для локальной истории операций и инвентаризации.

Go выбран ради простой поставки, типизированных операций и сетевой оркестрации. Python остаётся возможным инструментом тестового стенда, но не обязательной зависимостью VPS. Rust не требуется: фильтрация пакетов выполняется ядром, а не GUI-процессом.

На VPS не устанавливаются Node.js, SQLite-сервер или веб-панель Kenshi Shield. Версии библиотек и Go фиксируются при реализации по доступным поддерживаемым выпускам; номера версий в этой спецификации не выдумываются.

Первичная целевая матрица: локальный контроллер macOS/Linux; VPS Debian 12/13 и Ubuntu 24.04 с systemd, архитектуры amd64/arm64. Это план тестирования, не заявление о готовой поддержке. Применение разрешается только для комбинаций, прошедших интеграционные тесты.

## 4. Границы релизов

### Первый самостоятельный релиз

1. Локальные GUI/CLI с общим движком операций.
2. Подключение SSH, проверка host key и read-only инвентаризация.
3. Профили Panel, Remnanode с Nginx/Caddy, Remnanode без reverse proxy и Custom.
4. Явная модель открываемых портов, адресных исключений и сетевых путей.
5. Предпросмотр nftables, diff, проверки совместимости и политика TCP/25.
6. Backup, watchdog, атомарное применение своего ruleset и подтверждение результата.
7. Восстановление после сбоев, повторный запуск, история и обезличенный экспорт Markdown/JSON.
8. Установка из проверяемых релизных артефактов и инструкция восстановления через консоль VPS.

### Последующие самостоятельные модули

- CrowdSec: обнаружение существующей установки, acquisition, наблюдение, затем отдельно bouncer.
- Fail2Ban: выбранные сервисы, проверенные jail/action, IPv4/IPv6, отсутствие дублирования CrowdSec.
- Reverse proxy: отдельные HTTP-ограничения панели и подписок после проверки транспортов.
- Мониторинг и уведомления с контролем объёма и приватности данных.
- Performance: измерения, затем отдельные обратимые sysctl/BBR/RPS-профили.
- XanMod, SYNPROXY, внешние blocklist и провайдерские API: вне первого релиза.

Отложенные модули не показываются как работающие. Первый релиз может обнаруживать их и предупреждать о конфликтах, но не устанавливает их скрыто.

## 5. Компоненты и ответственность

| Компонент | Ответственность |
|---|---|
| GUI/CLI | Отображение состояния, выбор профиля, согласование плана и результата |
| Inventory | Сбор ограниченных сведений о системе без изменения конфигурации |
| Planner | Преобразование inventory и пожеланий в воспроизводимый план |
| Policy compiler | Типизированные порты/CIDR/интерфейсы в собственные nftables-правила |
| SSH transport | Проверка сервера, аутентификация, ограниченные по времени вызовы |
| Executor | Проверка плана, блокировка конкурентных операций, применение и журнал |
| Watchdog/recovery | Независимый от SSH откат неподтверждённой операции |
| Verification | Локальные и внешние проверки конкретного сервиса и транспорта |
| Local store/reporting | История, статусы, редактирование чувствительных данных при экспорте |

Исполнитель не является произвольным удалённым shell API. Операции и аргументы типизированы; пользовательские строки не подставляются в shell-команды, systemd units или nftables без разбора и валидации.

## 6. Инвентаризация и условия отказа

Сбор включает ОС, ядро, архитектуру, виртуализацию, systemd, версии сервисов, Docker network mode и published ports, backend firewall, interfaces, routes, SSH listeners, IPv4/IPv6, доступные команды, текущие правила и необходимые служебные соединения.

Не выводить полные docker inspect/compose config, окружение, секреты, ключи, адресные списки клиентов или подписочные URL. Сведения извлекаются выборочно, сырые конфигурации остаются на VPS.

Для каждого порта фиксируются протокол, адрес/interface привязки, назначение, владелец, источник доступа и сетевой путь. Обнаруженный listener сам по себе не становится разрешением на публичный доступ.

Отсутствие утилиты означает «проверка недоступна», а не её автоматическую установку. Установка зависимостей является отдельной согласованной операцией с перечнем пакетов и последствий.

Аудит не изменяет конфигурацию, не устанавливает пакеты и не перезапускает сервисы. Dry-run может создавать только явно обозначенные временные файлы проверки с ограниченными правами, не сохраняет boot-политику и не применяет ruleset. SSH-аутентификация и разрешённые сетевые пробы могут оставлять обычные системные журнальные записи; «read-only» не означает физического отсутствия любых записей ОС.

Неизвестная топология, конфликтующие firewall managers, недостаточные права, неопределённый SSH-путь или отсутствие рабочего восстановления блокируют применение, но не доступный read-only аудит.

WARP/WireGuard, policy routing, Docker overlay, rootless/macvlan/ipvlan и контейнерная виртуализация сначала классифицируются. Без проверенного адаптера доступны только аудит и рекомендации.

## 7. Baseline firewall

- Собственный namespace таблиц и файлов Kenshi Shield, без `flush ruleset`.
- Существующие таблицы Docker, UFW, firewalld, CrowdSec и сторонних инструментов не переписываются.
- `input`, `forward` и `output` рассматриваются отдельно. Учитываются DNAT, исходный published port и реальные направления интерфейсов.
- Backend Docker не переключается. При непроверенной комбинации backend/hooks применение запрещается.
- Разрешение в собственной base chain не считается обходом запрета другой таблицы. Проверяется полный путь обработки пакета.
- SSH разрешается только согласно подтверждённой административной политике. Адрес текущей SSH-сессии не получает доступ ко всем сервисам.
- Node API ограничивается адресами панели или подтверждённого управляющего туннеля. Фиксированный порт из примера не подставляется автоматически.
- Публичные Xray-порты отделяются от API, metrics, панели и подписок.
- После согласования allowlist входящие подключения вне неё запрещаются. Forward-фильтрация ограничена определёнными внешними путями к контейнерам; универсальный forward-drop без модели маршрутизации не применяется. Исходящий трафик в baseline разрешён за исключением согласованных egress-запретов.
- Сохраняются необходимые ICMP/ICMPv6, PMTU, ND, DHCP и router advertisement согласно роли интерфейса.
- NAT, DNS, ACME, NTP и межконтейнерные связи учитываются по обнаруженной конфигурации.
- Не включаются массовые автобаны за единичный SYN, глобальные лимиты VPN-трафика и универсальные bogon-правила на частных провайдерских сетях.
- Все динамические наборы, если будут добавлены, имеют ограничения размера, lifetime и скорости журналирования.

Закрытие порта прекращает сетевой доступ, но не останавливает listener. Отчёт различает «слушает», «разрешён политикой» и «проверен снаружи».

## 8. Исходящий TCP/25

Рекомендуемая политика: запрет прямого исходящего TCP/25 для серверов без прямой отправки почты. Перед применением нужны проверка соединений/почтовых сервисов и подтверждение пользователя. Отсутствие соединений в одном снимке не доказывает отсутствие потребности в почте.

465/587 не блокируются автоматически. Исключения ограничиваются согласованным назначением и адресом.

Правило охватывает поддержанные пути host egress и container forwarding по IPv4/IPv6. Для egress внутри зашифрованного туннеля требуется адаптер точки до шифрования или выходного узла; обычный host output-rule не объявляется достаточным.

Политика TCP/25 проверяется до общего разрешения established в соответствующем пути, чтобы не оставить существующую SMTP-сессию незаметным обходом. В diff явно указывается возможное прекращение текущих почтовых соединений. Массовая очистка conntrack запрещена.

После применения проверяются counters и контролируемое соединение с заранее согласованным тестовым endpoint без отправки писем. Проверяется сохранение нужного трафика. Тайм-аут на произвольном внешнем сервере сам по себе не доказывает работу правила.

## 9. Безопасность локального управления

- Loopback binding дополняется точной проверкой Host/Origin, запретом wildcard CORS и CSRF-защитой мутаций.
- Случайный одноразовый bootstrap-секрет открывает сессию; он не сохраняется в access-логах, истории операций или аналитике. Передача через fragment с немедленной очисткой URL; обмен только через локальный API.
- Cookie с HttpOnly и SameSite=Strict, ограниченный срок сессии, отсутствие сторонних скриптов и аналитики. CSP запрещает внешние исполняемые ресурсы.
- Аутентификация SSH через локальные ключи/агент. Не пересылать агент на VPS, не хранить root-пароли.
- Неизвестный host key требует проверки fingerprint; изменившийся ключ блокирует соединение до отдельного разрешения.
- Повышенные права требуются лишь операциям на VPS. GUI не запускается от root. Не выдаётся универсальное `NOPASSWD: ALL`.
- API-токены панели хранятся только в памяти либо системном credential store по явному выбору, никогда в SQLite или экспортируемых отчётах.
- Первая интеграция с Panel выполняет только чтение. Scope проверяется по установленной версии; при отсутствии read-only scopes предупреждаем о фактических полномочиях токена.
- Компрометация root VPS или рабочего компьютера не устраняется этим приложением и входит в явно описанные ограничения модели угроз.

## 10. Транзакции, подтверждение и восстановление

Состояния операции:

`planned -> validated -> backed_up -> armed -> applying -> awaiting_confirmation -> committed`

Ошибки после вооружения watchdog переводят операцию в `rolling_back -> rolled_back` либо `recovery_required`. Потерявший связь GUI отображает `unknown` как состояние наблюдения, не перезаписывая журнал VPS.

1. План содержит ID, digest содержимого, fingerprint целевого хоста, снимок предпосылок и точный список изменений.
2. Перед выполнением исполнитель повторно сверяет предпосылки и версии. Изменение конфигурации требует нового плана и подтверждения.
3. На хосте разрешена одна изменяющая операция. Повторный запрос с тем же ID возвращает её состояние; другой payload с тем же ID отклоняется.
4. Backup сохраняет предыдущее собственное ruleset, файлы, права и enabled/active состояния изменяемых units. Фиксируется также отсутствие ресурса до установки.
5. Backup принадлежит root, каталог недоступен другим пользователям; запрещены небезопасные symlink-пути. Нехватка места и ошибка сохранения останавливают операцию до мутаций.
6. Watchdog вооружается и проверяется до применения. Журнал записывается устойчиво до каждого опасного перехода.
7. Собственная nftables-транзакция проверяется `nft -c` и применяется атомарным batch. Это не делает файловые и systemd-изменения одной атомарной транзакцией: для них есть отдельные компенсирующие операции.
8. Pending-политика не становится постоянной загрузочной конфигурацией. Boot recovery, подготовленный до apply, восстанавливает последнюю committed-версию при незавершённой операции до обычной загрузки правил инструмента.
9. Проверяются новое независимое SSH-подключение, управляющий путь панели и выбранные пользовательские сервисы. Текущая established SSH-сессия не считается достаточной.
10. Лишь явное подтверждение конкретного плана при успешных обязательных проверках разрешает commit. Если невозможно проверить VPN-клиент, это отображается отдельно, а не выдаётся за успешную проверку протокола.
11. По deadline без commit выполняется откат. Закрытие GUI, сон компьютера, отмена и обрыв SSH не отключают watchdog.
12. Откат восстанавливает предыдущую собственную защиту, а не просто удаляет таблицу. Проверка firewall и persistence после отката обязательна.

При первой установке отсутствие прежних ресурсов Kenshi Shield является корректным сохранённым состоянием. Откат удаляет только вновь созданные собственные ресурсы и возвращает записанные состояния сервисов; чужая исходная защита сохраняется.

Обязательные post-checks входят в план до его подтверждения: новая SSH-сессия, проверка применённого ruleset, ожидаемые разрешённые/запрещённые пути и состояние persistence. Для профиля Panel добавляются HTTPS и согласованная аутентифицированная проверка API; для Remnanode проверяется управляющая связь от панели и выбранный VPN transport. Протокольную проверку выполняет интегрированный тестовый клиент либо оператор существующим клиентом с явной фиксацией результата. Отсутствие обязательной проверки не превращается в успех и не разрешает commit; автоматического снятия этого требования нет.

Гонка confirm/timeout/rollback разрешается под одной блокировкой с переходом состояния по ожидаемой версии. Частичный commit после сбоя восстанавливается по журналу; неподтверждённый вариант не становится последним рабочим состоянием.

Не обещаем откат всех побочных эффектов пакетного менеджера. Установка зависимостей отделена от firewall-транзакции; ранее существовавшие пакеты не удаляются. Provider snapshot является отдельным checkpoint, проверенным через провайдера или оператором, а не синонимом файлового backup.

В случае внешней правки принадлежащего инструменту ресурса обычный пользовательский rollback останавливается для разбора конфликта. В активном pending-окне watchdog восстанавливает сохранённую committed-версию собственных ресурсов; это поведение заранее показывается в плане.

## 11. Пользовательский сценарий

Постоянная боковая навигация: серверы, аудит, план изменений, операции, восстановление. Настройки редактируются в диалогах; основная навигация не прячется в flyout.

Мастер: подключение -> аудит -> профиль и разрешения -> diff/последствия -> проверки и backup -> применение -> проверка из новой сессии -> подтверждение.

Интерфейс на понятном русском языке. Технические команды доступны в подробностях. Показываются этап, последняя связь с VPS, deadline автоматического отката, причины запрета действия и способ восстановления.

Ошибки различаются: неверный host key, аутентификация, недостаточные права, неподдержанная схема, недоступная проверка, ошибка применения и неподтверждённое восстановление.

До apply отмена прекращает подготовку; после apply отмена запрашивает rollback. Отмена не означает немедленное уничтожение удалённого процесса. Retry сначала читает журнал, не запускает процедуру заново вслепую.

Экспорт по умолчанию скрывает адреса, домены, usernames и чувствительные пути. Секреты и полные подписочные URL не экспортируются ни в одном режиме.

## 12. Supply chain и публичный репозиторий

- Установочные инструкции не используют `curl | bash`, загрузку изменяемой `main` или автоматический переход на latest.
- Релиз включает версию, перечень платформ, SHA-256 checksums, SBOM, лицензии зависимостей и проверяемое свидетельство происхождения сборки.
- Checksums обнаруживают повреждение, но сами по себе не подтверждают доверенный источник. Проверка подписи/attestation привязана к конкретному репозиторию и разрешённому release workflow.
- GitHub Actions и зависимости фиксируются проверенными версиями/commit SHA; токены CI имеют минимальные permissions, повышение прав допускается лишь в защищённом release job.
- В CI входят тесты, анализ зависимостей и поиск секретов. Код из внешнего PR не получает release credentials.
- Обновления требуют явного действия, показывают изменения и не применяют новые firewall-политики автоматически.
- Реальные .env, backups, inventory, SQLite-файлы, ключи, client configs и приватные отчёты исключаются из репозитория.
- Проекту нужна явная лицензия перед публичным выпуском. Предлагается MIT; лицензия не добавляется и публикация не выполняется на этапе этой спецификации.
- Заимствованный код node-accelerator сохраняет MIT-уведомления. Первоначально переносим проверенные идеи, а не запускаем его установщик.

## 13. Проверки и критерии готовности

Unit/property/fuzz: разбор IP/CIDR/портов, запрет инъекций, детерминированный compiler, redaction, конечный автомат, конфликт ID и confirm/timeout.

GUI/API: загрузка, пустой аудит, успех, ошибка, отмена, двойное нажатие, retry, восстановление сессии, CSRF, Host/Origin, отсутствие токенов в логах и очистка bootstrap-fragment из URL после обмена.

Linux VM: host и Docker bridge, поддержанные backend firewall, IPv4/IPv6, закрытый published port, доступный разрешённый сервис, SMTP host/container, сохранение DNS/ACME и служебных сетевых функций.

Fault injection: остановка исполнителя после каждого этапа, обрыв SSH, reboot до/во время commit, заполненный диск, недоступный nft, отказ watchdog, внешняя правка конфигурации, два параллельных запроса, повторный rollback.

Canary: только согласованный тестовый VPS и контролируемые endpoints. Проверяются новая SSH-сессия, реальная связь Panel/Node, HTTPS и VPN handshake с передачей данных выбранного транспорта. Атакующий трафик на production не генерируется.

Готовность к выпуску требует доказанного восстановления после reboot и разрыва SSH. `go test`, frontend build, `nft -c`, healthy container и HTTP 200 по отдельности не доказывают работающую защиту или VPN.

Непроверенные платформы и протоколы маркируются «не проверено»; кнопка apply для непроверенной сетевой схемы недоступна.

## 14. Источники и выполненная проверка

Проверено чтением исходников node-accelerator на commit `f64fec3c84ab69c4b53be04cc07906d51e00c05c`: install.sh, common.sh, diagnose.sh, protect.sh, optimize.sh, rollback.sh и README.

Подтверждены статически: установка пакетов при DRY_RUN, разрешение node port без ограничения источника, неполный safety rollback/persistence, разрешающий forward и несоответствие download namespace.
